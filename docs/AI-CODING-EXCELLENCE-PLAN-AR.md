# خطة رفع ذكاء البرمجة إلى مستوى استثنائي — GpTMax مقابل النماذج الأمريكية

> وثيقة تقييم وخطة تنفيذ لرفع قدرة الوكيل البرمجي في GpTMax (أندرويد، محلي أولاً) إلى مستوى تنافسي
> مع أدوات البرمجة الأمريكية الرائدة: Claude Code، OpenAI Codex، GitHub Copilot، Gemini CLI.
> تبنى على حالة المستودع الفعلية (فرعا `fix/review-safety` و`studio-v1` بعد إغلاق إصلاحات المراجعة الستة).

---

## 1) الملخص التنفيذي

GpTMax يملك اليوم أساساً أمنياً ناضجاً نادراً في التطبيقات المحلية: حجب موحد للمسارات الحساسة،
بصمات SHA-256 مع تحقق بالقراءة بعد الكتابة، مجلة تراجع قابلة للاستعادة، بوابة موافقة على الكتابات،
وفهرس سياق محلي بحدود صارمة. لكن الفجوة الحقيقية مع الأدوات الأمريكية ليست في الأمان بل في
**ثلاث ركائز**: حجم السياق الفعّال، عمق حلقة التخطيط والتنفيذ، وجودة حلقة التحقق الذاتي.
هذه الخطة تسدّ الفجوة عبر ستة مسارات عمل على 12 شهراً، بمعايير قبول قابلة للقياس لكل مرحلة،
وبدون المساس بمبدأ «الخصوصية محلياً أولاً».

**الهدف النهائي**: إتمام 60% من مهام مجموعة التقييم الداخلية (100 مهمة بأسلوب SWE-bench مصغّر)
دون تدخل بشري على طراز Snapdragon 8-class، مع زمن استجابة تفاعلي وضمانات أمان كاملة.

## 2) تقييم الحالة الحالية (مؤسّس على الكود)

| المحور | الوضع اليوم | القوة | الفجوة |
|---|---|---|---|
| الاستدلال | llama.cpp عبر JNI، GGUF مستورد بتحقق SHA-256، arm64-v8a | خصوصية كاملة، لا إنترنت | نماذج صغيرة (Q4)، نافذة سياق قصيرة |
| حلقة الوكيل | `AgentRuntime`: حدود 8 أدوات/جلسة، 384 توكن مخرجات، ميزانية ملاحظات 6000 حرف | إلغاء لكل طلب، دفتر مهام JSONL | خطوة واحدة لكل قرار، لا تخطيط متعدد المراحل |
| السياق | `ProjectContextEngine`: فهرسة 1200 ملف × 64KB، recall/remember/checkpoint | استرجاع نصي محلي | لا AST، لا تضمينات، لا خريطة مستودع ذكية |
| الأدوات | قراءة/بحث/قائمة/كتابة/استبدال + أدوات السياق الست | أمان كتابة من الطراز الأول | لا تعديل diff، لا طرفية معزولة، لا تشغيل اختبارات |
| التحقق | لا حلقة بناء/اختبار | — | الأدوات الأمريكية تُصلح ذاتها عبر «بناء→فشل→إصلاح» |
| القياس | `durationMs` لكل أداة + دفتر مهام | أساس جيد | لا مجموعة تقييم معيارية، لا لوحة جودة |
| الأمان | سياسة حساسة موحدة + مجلة تراجع + بوابة موافقة | **أفضل من كثير من الأدوات السحابية** | الحفاظ عليها أثناء التوسع |

## 3) تحليل الفجوة مقابل النماذج الأمريكية

الفجوات الحاسمة مرتبة حسب الأثر على جودة المهام المكتملة:

1. **السياق الفعّال** — Claude Code وCodex يعملان بسياق 200K+ توكن مع خرائط مستودع ذكية؛
   نافذتنا المحلية أصغر بعشرات المراحل. الحل ليس «نافذة أكبر» بل **استرجاع أدق**: ما يصل
   للنموذج يجب أن يكون أهم 5% من المستودع المرتبط بالمهمة.
2. **حلقة التخطيط-التنفيذ-التحقق** — الأدوات الأمريكية تنفذ دورة كاملة: خطة→تنفيذ→بناء→اختبار→
   إصلاح ذاتي، عشرات الدورات للمهمة. حلقتنا اليوم تنفيذ أحادي الاتجاه بلا تغذية راجعة.
3. **جودة الأدوات** — التعديل عبر diff دقيق (وليس إعادة كتابة ملف كامل) يخفض الأخطاء المدمرة،
   وتشغيل الاختبارات يمنح النموذج «عيوناً» على نتيجة عمله.
4. **موثوقية الاستدعاءات** — النماذج الأمريكية مُدربة على استخدام الأدوات؛ نماذجنا المحلية
   تحتاج قوالب استدعاء صارمة وإعادة محاولة ذكية وتنسيقات مخرجات مقيّدة (Grammar/GBNF).

## 4) مسارات العمل الستة (12 شهراً)

### M1 — تثبيت الجودة (أسبوعان) — البوابة لكل ما بعدها
- تفعيل `docs/ci/android-build.yml` كمسار CI فعلي (lint + release + محاكي).
- مجموعة تقييم داخلية v0: 20 مهمة برمجة حقيقية على مشاريع مرجعية، مع مصحح آلي للنتيجة.
- خط أساس أداء على الجهاز: توكن/ثانية، زمن أول استجابة، استهلاك ذاكرة لكل حجم نموذج.

### M2 — محرك السياق (شهر 1–2)
- خريطة مستودع هرمية (مجلدات→ملفات→رموز) بحدود توكن قابلة للضبط بدل القائمة المسطحة.
- فصل الكود إلى أجزاء واعية بالبنية (دوال/أصناف) عبر محلل خفيف لـ Kotlin/Java/Python.
- استرجاع هجين: BM25 نصي + تضمينات محلية صغيرة، مع دمج النتائج في ميزانية موحدة.
- رفع نافذة السياق لنماذج 32K محلية (Qwen2.5-Coder) مع إدارة KV-cache فعالة.

### M3 — حلقة الوكيل (شهر 2–4)
- فصل الأدوار: مخطط (يخطط خطوتين أماماً) → منفذ (أداة واحدة بدقة) → مدقق (يقرأ النتيجة ويقرر).
- انعكاس (Reflexion) بعد كل فشل أداة: ماذا حدث، ما البديل، إعادة المحاولة بحد أقصى 3.
- أداة `file.edit` جديدة بأسلوب diff موحّد (بحث/استبدال بدقة سطرية) على قمة حارس الكتابة الحالي.
- طرفية معزولة (قيود + قائمة سماح + مهلة + حجم مخرجات) لتشغيل أوامر قراءة فقط أولاً.

### M4 — حلقة التحقق الذاتي (شهر 4–6)
- تشغيل `gradle`/`pytest` من الطرفية المعزولة وإرجاع الأخطاء المختصرة للنموذج.
- دورة إصلاح ذاتي: بناء→تحليل الخطأ→تعديل→إعادة بناء، بحد دورات وميزانية توكن.
- دمج نتائج تحليل ثابت (Android Lint/ktlint) كملاحظات مقيّدة قبل التسليم.

### M5 — القياس والمعايرة (شهر 6–9)
- توسيع مجموعة التقييم إلى 100 مهمة (SWE-bench مصغّر عربي/إنجليزي) مع بوابات انحدار في CI.
- لوحة جودة: نسبة الإنجاز، متوسط الدورات، تكلفة التوكن، معدل التراجعات.
- مقارنة أسبوعية آلية: النموذج المحلي مقابل مسار سحابي اختياري صريح الموافقة.

### M6 — النماذج والتوسع (شهر 9–12)
- اعتماد Qwen2.5-Coder-7B/14B بترميز Q4_K_M كخط أساس محلي، مع فك ترميز تخميني (speculative).
- سياسة تصعيد سحابي: المهام الكبيرة فقط (تخطيط معماري، مراجعة) تُعرض على المستخدم لإرسالها اختيارياً.
- تعدد الوكلاء عند الحاجة: وكيل بحث + وكيل تنفيذ + وكيل مراجعة، بميزانيات منفصلة.

## 5) معايير القبول لكل مرحلة

| المرحلة | المعيار الكمي | المعيار النوعي |
|---|---|---|
| M1 | CI أخضر شامل + 20 مهمة بتقييم آلي | خط أساس أداء موثق على 3 أجهزة |
| M2 | استرجاع الملف الصحيح ضمن أعلى 5 نتائج في 90% من الاستعلامات | خريطة مستودع ≤ 3K توكن لمشروع 50 ملف |
| M3 | إنجاز 35% من مجموعة التقييم دون تدخل | لا خرق أمني واحد في فحص مسارات التراجع |
| M4 | 60% من أخطاء البناء تُصلح ذاتياً خلال ≤ 3 دورات | كل تعديل يمر عبر بصمة + تحقق قراءة |
| M5 | **60% إنجاز كامل** على 100 مهمة + بوابات انحدار خضراء | لوحة جودة حية في الإعدادات |
| M6 | ≥ 15 توكن/ثانية للنموذج 7B على Snapdragon 8-class | التصعيد السحابي صريح الموافقة 100% |

## 6) المخاطر والتخفيف

| خطر | الاحتمال | التخفيف |
|---|---|---|
| نافذة السياق المحلية تبقى عائق النوعية | مرتفع | M2 كاملة قبل أي توسيع أدوات؛ القياس أولاً |
| نماذج 7B غير موثوقة في استدعاء الأدوات | مرتفع | قوالب GBNF مقيّدة + إعادة محاولة + تحقق مخرجات |
| الطرفية المعزولة ثغرة محتملة | متوسط | قائمة سماح صارمة، مهلة، بلا شبكة، بوابة موافقة على الكتابة |
| انزلاق الميزانية على الجهاز (بطارية/حرارة) | متوسط | حزام ميزانية توكن/جلسة + إيقاف تلقائي عند الحرارة |
| تراجع الأمان أثناء التوسع | منخفض | اختبارات المراجعة الستة بوابات CI إلزامية لكل PR |

## 7) ترتيب التنفيذ الفوري (الأسبوعان القادمان)

1. تفعيل ملف CI المجهز (`mv docs/ci/android-build.yml .github/workflows/android-build.yml`) ودمج فرع الإصلاحات.
2. بناء مجموعة التقييم v0 (20 مهمة) ومصحح النتائج الآلي.
3. قياس خط الأساس: توكن/ثانية لكل نموذج مثبت، وزمن المهام الثلاث الأولى.
4. بدء خريطة المستودع الهرمية (M2) على فرع `feat/context-engine`.

> **قاعدة الإغلاق**: لا مرحلة تُعلن منجزة إلا باختباراتها الخضراء ومؤشرها الكمي الموثق —
> نفس المعيار الذي أغلق إصلاحات المراجعة الستة به.
